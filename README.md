# Go Performance Lab 🚀

Практический стенд для **исследования и оптимизации производительности Go-сервисов**.

Проект позволяет не просто посмотреть, как работает `pprof`, а пройти полный цикл:

**создать нагрузку → снять профиль → найти узкое место → проанализировать код → проверить результат.**

Он будет полезен разработчикам Go, которые хотят научиться находить причины высокой загрузки CPU, расхода памяти, блокировок, большого количества горутин и повышенных задержек.

---

## 🎯 Что вы получите

После запуска проекта вы сможете на практике:

* находить функции, которые потребляют больше всего CPU;
* определять, какие участки кода создают повышенное потребление памяти;
* анализировать работу Garbage Collector через heap-профили;
* находить блокировки и конкуренцию между горутинами;
* исследовать создание горутин и потоков;
* анализировать задержки и точки ожидания;
* изучать связи между функциями через call graph;
* находить «горячие» участки кода через flamegraph;
* сравнивать поведение приложения до и после оптимизации;
* использовать `go tool pprof` для анализа реального профиля Go-приложения;
* запускать готовые сценарии профилирования без необходимости самостоятельно писать тестовый сервис.

По сути, репозиторий можно использовать как **лабораторный стенд для performance engineering в Go**.

---

## 🔎 Какие проблемы помогает исследовать

Проект специально содержит HTTP-эндпоинты, которые создают разные типы нагрузки.

| Сценарий              | Что можно исследовать             |
| --------------------- | --------------------------------- |
| `/work`               | загрузку CPU и горячие функции    |
| `/alloc`              | выделение памяти и работу GC      |
| `/sleep`              | задержки и ожидание               |
| `/debug/pprof/`       | стандартные Go-профили            |
| `/debug/threadcreate` | создание горутин/потоков          |
| `/debug/mutex`        | конкуренцию за mutex              |
| `/metrics`            | метрики приложения для Prometheus |

Это позволяет воспроизводить нагрузку и получать профили, которые действительно содержат данные для анализа.

## 📊 Какие профили можно получить

### CPU

Показывает, где приложение проводит процессорное время.

Используется для поиска:

* CPU-heavy функций;
* неоптимальных алгоритмов;
* дорогих вычислений;
* лишних вызовов функций;
* участков кода, которые становятся bottleneck при нагрузке.

Получение профиля:

```bash
curl "http://localhost:8080/debug/pprof/profile?seconds=30" -o cpu.prof
```

Анализ:

```bash
go tool pprof -http=:8081 ./bin/service cpu.prof
```

В веб-интерфейсе доступны:

* Flame Graph;
* Top;
* Call Graph;
* Source;
* другие представления профиля.

> Важно: CPU-профиль необходимо снимать одновременно с нагрузкой. Например:

```bash
for i in {1..5}; do
    curl http://localhost:8080/work
done
```

Без нагрузки профиль может содержать мало или совсем не содержать полезных CPU samples.

## 🧠 Heap / Memory

Heap-профиль помогает понять, какие участки приложения используют память.

Он полезен для исследования:

* большого количества аллокаций;
* роста потребления памяти;
* объектов, которые занимают значительный объём heap;
* поведения приложения под нагрузкой;
* возможных источников memory pressure.

Получение:

```bash
curl http://localhost:8080/debug/pprof/heap -o heap.prof
```

Анализ:

```bash
go tool pprof -http=:8081 ./bin/service heap.prof
```

---

## 🔒 Block Profile

Block profile показывает, где горутины проводят время в ожидании синхронизации.

Он помогает исследовать:

* ожидание mutex;
* ожидание каналов;
* конкурентные участки приложения;
* места, где синхронизация увеличивает latency.

Получение:

```bash
curl "http://localhost:8080/debug/pprof/block?seconds=30" -o block.prof
```

Анализ:

```bash
go tool pprof -http=:8081 ./bin/service block.prof
```

Для получения информативного профиля нужна конкурентная нагрузка.

---

## 🔐 Mutex Profile

Mutex profile предназначен для анализа конкуренции за мьютексы.

Он помогает ответить на вопросы:

* какой mutex является узким местом;
* какие функции дольше всего ждут блокировку;
* где конкуренция между горутинами влияет на производительность.

Получение:

```bash
curl http://localhost:8080/debug/mutex -o mutex.prof
```

Анализ:

```bash
go tool pprof -http=:8081 ./bin/service mutex.prof
```

---

## 🧵 Goroutine Profile

Goroutine profile позволяет посмотреть состояние и распределение горутин.

Он полезен при исследовании:

* большого количества горутин;
* зависших или ожидающих горутин;
* конкурентного поведения приложения;
* потенциальных проблем с жизненным циклом горутин.

Получение:

```bash
curl http://localhost:8080/debug/pprof/goroutine -o goroutine.prof
```

Анализ:

```bash
go tool pprof -http=:8081 ./bin/service goroutine.prof
```

## 📈 Как использовать проект для поиска проблемы

Типичный сценарий работы:

```text
        Go-сервис
            │
            ▼
     Создание нагрузки
            │
            ▼
       pprof profile
            │
            ▼
    Flame Graph / Top
            │
            ▼
     Поиск bottleneck
            │
            ▼
      Оптимизация кода
            │
            ▼
     Повторное измерение
```

Например, если сервис неожиданно начал потреблять много CPU:

1. запускаем сервис;
2. создаём нагрузку через `/work`;
3. снимаем `cpu.prof`;
4. открываем профиль через `go tool pprof`;
5. смотрим `Top` и Flame Graph;
6. определяем наиболее затратные функции;
7. оптимизируем код;
8. повторяем профилирование;
9. сравниваем результаты.

Таким образом, проект можно использовать как основу для практического изучения **performance profiling**, а не только как пример подключения `net/http/pprof`.

## 🧪 Бенчмарки

Проект также содержит Go-бенчмарки.

Запуск:

```bash
make bench
```

Флаг:

```text
-bench=.
```

запускает все доступные бенчмарки.

Флаг:

```text
-benchmem
```

добавляет измерение аллокаций и использования памяти.

Это позволяет дополнить runtime-профилирование микробенчмарками и сравнивать изменения непосредственно на уровне отдельных функций.

## 📊 Prometheus

Сервис предоставляет endpoint:

```text
/metrics
```

Метрики можно использовать вместе с Prometheus и Grafana для наблюдения за приложением.

Например:

```text
http_requests_total
```

показывает количество HTTP-запросов.

Это позволяет сочетать два подхода:

```text
Метрики
   │
   ├── показывают, ЧТО происходит
   │
   ▼
pprof
   │
   └── помогает понять, ГДЕ это происходит
```

## ⚠️ Важный принцип профилирования

Профиль без подходящей нагрузки может оказаться практически бесполезным.

Например, для CPU profiling сначала нужно создать CPU-нагрузку:

```bash
curl http://localhost:8080/work
```

и только затем снимать профиль.

То же относится к block и mutex profiling: чтобы увидеть проблему, приложение должно реально испытывать соответствующую конкуренцию.

Поэтому рекомендуемый цикл:

```text
Нагрузка
   ↓
Профиль
   ↓
Анализ
   ↓
Изменение кода
   ↓
Повторный профиль
   ↓
Сравнение результата
```
